# SukotSystem — מוקד בדיקת סוכות

פרויקט גמר בקורס .NET — Web API Development.

## תיאור המערכת

SukotSystem הוא השרת (ASP.NET Core Web API) עבור "מוקד הסוכות" — שירות שמחבר בין אנשים לבין רבנים שמגיעים לבדוק האם הסוכה שלהם כשרה הלכתית. לקוח נרשם ופותח בקשת בדיקה עם עיר, כתובת, וסימון האם נדרש מכשיר לייזר למדידת סכך פסול; הבקשה נעשית גלויה לרבנים, וכל רב פנוי יכול "לקחת על עצמו" בקשה פתוחה, שאז ננעלת אליו ונעלמת מרשימת הבקשות הפנויות של כל שאר הרבנים. בנוסף, מזכירות קולטות בקשות עבור פונים בטלפון שלא נרשמו במערכת, ושלוש/שתי מנהלות-על רואות את כל המערכת ומנהלות את סגל הרבנים והמזכירות ואת רשימת הערים.

## תפקידים במערכת

| תפקיד | מה הוא עושה |
|---|---|
| **לקוח (Customer)** | נרשם ומתחבר, פותח בקשת בדיקה עבור עצמו, יכול לערוך אותה כל עוד לא נתפסה על ידי רב |
| **רב (Rabbi)** | רואה בקשות פנויות (מסונן לפי עיר או לא), תופס בקשה (המשאב המוגבל — ראו למטה), ומסמן אותה כהושלמה עם הערות |
| **מזכירה (Secretary)** | קולטת בקשה חדשה עבור מתקשר בטלפון שלא נרשם (ללא CustomerId, עם שם וטלפון של המתקשר), ורואה את כל ההזמנות במערכת לצפייה בלבד |
| **מנהלת-על (Admin)** | רואה את כל ההזמנות במערכת, מנהלת את סגל הרבנים (הוספה/השבתה/הפעלה), את המזכירות (הוספה), ואת רשימת הערים |

רק מנהלת-על מוסיפה רבנים ומזכירות — אין הרשמה עצמית לשני התפקידים האלה. לקוח הוא התפקיד היחיד עם הרשמה עצמית (`POST /api/Customer`).

## המשאב המוגבל ואיך המערכת מטפלת בתחרות עליו (Part C)

המשאב המוגבל הוא בקשת הבדיקה (**Order** / הזמנה) עצמה, ברגע שהיא פתוחה (`Status = New`) — כל רב פנוי יכול לתפוס אותה, אבל רק אחד יכול להצליח. התחרות מתרחשת ב-`POST /api/Orders/{id}/claim`: אם שני רבנים לוחצים "אני לוקח את זה" במרחק מילישניות זה מזה, שניהם עוברים את אותה בדיקת "האם זה עדיין New", אבל רק ה-`SaveChangesAsync` הראשון באמת מעדכן את השורה, כי לכל הזמנה יש שדה `Version` (`Guid`, מסומן ב-`[ConcurrencyCheck]`) שמוחלף בכל שמירה (ע"י override של `SaveChangesAsync` ב-`DataContex`, כך שאף Service לא צריך לזכור לעשות זאת בעצמו). השמירה השנייה מנסה לעדכן שורה עם ערך `Version` שכבר לא קיים, EF Core זורק `DbUpdateConcurrencyException`, והשרת מגיב עם **409 Conflict** והודעה ברורה שהבקשה כבר נתפסה — לעולם לא תפיסה כפולה שקטה.

הבדיקה העסקית (`Status != New`) וההצלה מתבצעות על אותו Entity שנטען פעם אחת (tracked), ולא על שני קריאות נפרדות — כדי שהבדיקה תהיה חלק מאותה "עסקה" ולא תיבדק על נתונים ישנים.

## הרצה מקומית

### דרישות מוקדמות

- .NET 8 SDK
- PostgreSQL (מקומי, או דרך Docker: `docker run --name pg -e POSTGRES_PASSWORD=<סיסמה> -p 5432:5432 -d postgres:16`)
- (לקליינט, אופציונלי): Node.js — ראו את ריפוזיטורי ה-React הנפרד

### הגדרת מחרוזת חיבור ומפתח JWT (User Secrets — לעולם לא ב-appsettings.json)

```bash
cd SukotSystemApi
dotnet user-secrets init
dotnet user-secrets set "ConnectionStrings:Default" "Host=localhost;Port=5432;Database=SukotSystemDb;Username=postgres;Password=<הסיסמה שלכם>"
dotnet user-secrets set "Jwt:Key" "<מחרוזת סודית ארוכה כלשהי, לפחות 32 תווים>"
```

### הרצת המיגרציות

מהתיקייה השורשית של הפתרון (הרצה ראשונה בלבד — אחרי מכן `dotnet ef database update` מספיק כשמיגרציה חדשה נוספת):

```bash
dotnet ef database update -p SukotSystemData -s SukotSystemApi
```

זה יוצר את הסכמה המלאה **וגם מזרע** אוטומטית: רשימה של 194 ערים/מועצות מקומיות אמיתיות בישראל, ושני חשבונות מנהלת-על מוכנים לשימוש (ראו "משתמשי דמו" למטה) — אין צורך בהתערבות ידנית במסד הנתונים לפני שהמערכת עולה.

### הרצת השרת

```bash
dotnet run --project SukotSystemApi
```

Swagger נפתח אוטומטית (`launchSettings.json` מגדיר `launchUrl: swagger`), בכתובות:
- HTTPS: `https://localhost:7262/swagger`
- HTTP: `http://localhost:5114/swagger`

לקריאה מוגנת (`[Authorize]`): מתחברים דרך `POST /api/Auth/login`, מעתיקים את ה-`token` מהתשובה, לוחצים על כפתור "Authorize" ב-Swagger ומדביקים רק את הטוקן עצמו (בלי המילה `Bearer`).

## משתמשי דמו

### מנהלת-על — כבר מזורעות במסד הנתונים, מוכנות לשימוש מיידי

| טלפון | סיסמה | שם |
|---|---|---|
| `0556751030` | `1234` | אלף שין |
| `0500000000` | `1234` | מפתחים |

### רב, מזכירה, לקוח — נוצרים לאחר ההרצה הראשונה (אין הרשמה עצמית לרב/מזכירה)

1. מתחברים כמנהלת-על (למעלה) בקליינט או ב-Swagger.
2. **רב**: `POST /api/Rabbis` (או מסך "ניהול רבנים" בקליינט) — לדוגמה `firstName: "רב"`, `lastName: "לדוגמה"`, `phone: "0501111111"`, `homeCityId: 1`, `password: "demo1234"`.
3. **מזכירה**: `POST /api/Secretaries` (או מסך "ניהול מזכירות" בקליינט) — לדוגמה `phone: "0502222222"`, `password: "demo1234"`.
4. **לקוח**: נרשם עצמאית דרך `POST /api/Customer` (או מסך ההרשמה בקליינט) — כל טלפון וסיסמה לבחירה.

לאחר מכן, כל תפקיד מתחבר דרך אותו `POST /api/Auth/login` (טלפון + סיסמה) — טלפון אחד קובע את התפקיד, לא צריך לבחור תפקיד בטופס ההתחברות עצמו.

## לוגים (NLog)

כל בקשה נכנסת נרשמת עם `CorrelationId` ייחודי (נוצר ע"י middleware ומצורף לכל שורות הלוג של אותה בקשה), כל שגיאה שנתפסת נרשמת ברמת Error, וכל התנגשות משאב (409, כולל תפיסה כפולה של בקשה) נרשמת ברמת Warning. קבצי הלוג נמצאים תחת `SukotSystemApi/bin/Debug/net8.0/logs/`. סיסמאות, טוקנים ותוכן בקשות הרשמה לעולם לא נכתבים ללוג.

## מבנה הפתרון

```
SukotSystem.sln
SukotSystemCore/     Models, Enums, Exceptions, DTOs, Repositories/Services interfaces — ללא תלות בשום פרויקט אחר
SukotSystemData/      DbContext (DataContex), Repositories, Migrations — תלוי ב-Core בלבד
SukotSystemService/   לוגיקה עסקית (Services) — תלוי ב-Core בלבד
SukotSystemApi/       Controllers, Middlewares, Program.cs — תלוי ב-Service וב-Core; מכיר את Data רק לצורך רישום DI ב-Program.cs
```

Controller אף פעם לא מזריק `DbContext` ישירות — תמיד דרך Service. `Core` לא מפנה לשום חבילת EF Core.
